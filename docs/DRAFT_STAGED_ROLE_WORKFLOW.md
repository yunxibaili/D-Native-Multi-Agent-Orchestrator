## 1. 讨论目标与职责边界

用户可能只提供大概需求。LAYA 应先组织适合的模型参与研究、澄清和方案表达，让用户理解要做什么、预期效果是什么；确认后才进入实施计划、阶段拆分和开发。

- LAYA 是唯一任务级决策入口，负责选择所需职位、阶段边界、依赖及具体 Agent × Model；其他角色提供分析和交付物，不另设指挥系统。
- 用户选择可用 Agent 和模型范围，LAYA 在用户允许的范围内分配，不以“只能免费”作为本草案的产品要求；费用仍服从实际授权，不由本草案新增支出权限。
- 角色、Agent、模型分开理解。职位随任务类型变化，同一个模型可以承担多个职责，不要求每个职位常驻一个 Agent。
- Codex 固定使用用户指定的 GPT-6.1 Sol 承担独立审核，不承担同轮开发；此名称不等于已经核验的 CLI 模型标识。
- 写代码的 Worker 必须核对相关源码、调用点和必要技术资料，并完成相关自测，不能只凭上游研究摘要实施。

## 2. 建议工作流与用户确认点

以下为大型开发项目的讨论流程，具体阶段数量和参与职位由 LAYA 按任务决定；不要求所有任务套用完整流程。

| 环节 | 可参与的职责 | 交付物与停止点 |
|---|---|---|
| 需求探索与澄清 | 需求分析、资料研究；按需加入方案分析、交互设计 | 原始目标的理解、关键问题、可选方向、可行性与限制；LAYA 集中向用户澄清 |
| 需求与效果方案 | 需求策划、设计、可行性分析、需求与规范监督 | 可供用户决策的需求、使用流程、范围、验收标准及预期效果；等待用户确认 |
| 总体实施计划 | 方案分析、相关开发代表、测试、监督者 | 实现路线、关键取舍、依赖与风险；等待用户确认总体计划 |
| 阶段划分与当前阶段细化 | LAYA 组织相关角色 | 各阶段目标和交付；当前阶段详细任务、依赖、模型分工与验收方法；等待用户授权当前阶段 |
| 当前阶段开发与验证 | 对应开发者、测试、监督者、Codex 独立审核 | 仅实施获授权阶段，交付成果、测试证据、审核结果和遗留问题 |
| 用户验收与后续选择 | LAYA 汇总材料，用户决策 | 用户决定接受、要求调整、暂停或进入下一阶段；不自动跨阶段开发 |

确认边界：

- 认可需求与效果，只允许继续形成实施计划，不等于允许写产品代码。
- 认可总体计划，不等于批准整项目实施；后续仍须确认当前阶段任务与执行范围。
- 批准当前阶段，不等于批准下一阶段；不要求每个小任务都重复确认。
- 用户确认针对已经展示的材料与范围，不能将沉默、模型自评或“文件已生成”当作批准。
- 需求、范围或实施路线发生实质变化时，提出变更并交用户确认，不能沿用旧确认继续扩大执行。

### 需求阶段的模型协作

研究者调查现成实现、工具接口和限制；需求分析者梳理使用场景、功能边界及待确认问题；方案分析者比较可行路径；设计者表达使用效果；监督者检查是否遗漏或歪曲原始要求。LAYA 汇总为一份材料，避免模型分别向用户重复提问。

区分用户已明确的要求、模型提出的建议、尚未确认的假设和未知项。需求达到可决策程度即可交用户审阅，不以追求绝对完整为由无限调查，也不将未知项伪装成确定需求。

预期效果也是交付物：有界面项目可用流程图、线框图；命令行工具可用输入输出及失败提示示例；数据任务可用结果样例。设计示意明确标注为预期效果，不作为已实现证据。需要写原型、搭工程或安装依赖时，应列为待用户授权的验证任务。

## 3. 职位选择、模型匹配与阶段拆分

### 按任务选择职位

大型开发可以包含资料研究、需求策划、方案分析、前端开发、后端开发、测试验证、需求与规范监督、独立审核。前后端可由同一执行者先后承担，不据此开放并行写。

纯调研任务可以使用资料收集、比较分析、事实核验；故障任务可以使用问题复现、根因分析、修复与回归验证。简单任务可合并职责，不为了用上全部模型而凑职位。

### 以有出处的能力描述匹配模型

选择顺序：任务需要的职位与能力 → 用户允许的 Agent × Model 候选 → 实际工具及兼容条件 → 分配结果。

- 优先参考具体模型版本的官方说明、技术报告及可信社区实测，保留来源、日期、测试条件和适用限制；不凭厂商印象或模型自报能力分工。
- 官方定位和社区经验可作为初始分配依据，不要求先自行组织完整模型评测；已有可靠执行证据可补充和修正判断。
- 搜索职位需有实际搜索和来源核验工具；能写代码不代表能运行测试；模型具备某能力不等于当前 Agent 暴露了对应工具。
- 同一模型可有多个强项。资料存在分歧时保留不确定性，不编造精确能力分数或绝对排名。
- 没有满足任务要求的合法候选时报告缺口，由用户决定如何处理，不擅自扩大模型范围或降低必要要求。

例如，具备 Google Search grounding 的 Gemini 组合可进入研究候选；具体编程模型可进入开发候选。此类依据不构成某厂商模型在所有版本、所有 Agent 中都最强的结论。

### LAYA 划分阶段的建议规则

- 按可交付、可验证的成果划分，每阶段结束时用户能查看或验证明确结果。
- 优先打通最小完整流程，再扩展能力，不默认先做完全部后端再验证使用流程。
- 关键未知先调查；需要原型才能验证时，先说明验证目标、范围和产物，再由用户授权。
- 总体路线清楚，当前阶段任务详细；远期阶段保留目标、依赖与验收方向，临近执行再细化。
- 阶段大小由依赖、风险和验证成本决定，不按固定任务数、模型数或时间长度机械切分。
- 阶段与现有执行 Round 不预设为一一对应；后续设计应复用现有执行、证据与 Human Gate 契约，不能绕过当前关口。

## 4. 需求与规范监督

监督者从需求阶段参与，覆盖方案、任务交接、开发与宣告完成；与开发分开会话，不替代 LAYA 派工或 Codex 独立审核。

检查依据包括用户原始要求、后续明确指令、已确认的需求与计划、验收标准、项目规范，以及实际产物、工具记录和测试证据。不能仅检查 LAYA 或开发者的摘要。

重点检查需求遗漏与偏移、擅自扩大范围、违反规范、上下游接口矛盾，以及没有证据的完成或测试通过声明。

建议在方案确认、阶段交接、重要需求变更和宣告完成时检查；出现明确违规迹象可提前触发，避免每一步重复整项目审查。

**用户已选择：监督者发现需要纠偏的问题，暂停相关任务，所有纠偏交用户决定。** 报告应说明违反哪条要求、事实证据、影响与可选处理方式；尚未证实的问题标为疑点，不当作已确认违规。监督者不自行修改代码、需求或计划，不重新派工，不触发自动返工循环。暂停的实际执行机制留待后续任务设计与验证，本草案不声称已有运行能力。

## 7. 一轮结束时应交付什么

### 7.1 用户首先看到的交付摘要

用户收到的是“成果与决策材料”，不是几个模型对话记录的拼接。简单轮次保持简短；复杂轮次先给一屏摘要，再提供可展开的材料和证据入口。

| 必须回答的问题 | 建议呈现内容 |
|---|---|
| 本轮做的是哪件事 | 项目/阶段/轮次与已确认需求、计划的对应关系，本次获授权范围 |
| 现在到哪一步了 | 实际结果：完成待验收、部分完成、失败、取消、等待材料/用户或状态未知；这是展示用语，不擅自扩充现有 Task 状态 |
| 实际交付了什么 | 可打开的文件、差异、报告、构建产物、演示入口或设计材料；说明有效版本和如何查看/使用 |
| 满足了哪些要求 | 验收条目对应的结果与证据；不适用、未测、受阻和未完成明确标出，避免只报任务数量 |
| 改了什么、影响什么 | 实际改动范围、接口/配置/数据影响、必要的启动或迁移说明；没有改代码的轮次明确是设计或调研交付 |
| 验证到什么程度 | 实际测试命令、结果、所测版本/环境、失败与未运行原因；命令成功不能自动推出业务正确 |
| 谁作了哪些判断 | Worker 自述、系统观察、监督者发现、Codex 审核分别列出；审核请求、审核完成、verdict 与证据记录也分开 |
| 还剩什么问题 | 阻塞与非阻塞项、部分成功、未交付与假设；用户接受限制不把未测项目改写为通过 |
| 消耗与环境有什么限制 | 已知耗时、调用/重试及供应商报告的费用/用量，缺失部分标未知；统计范围包含研究、决策、测试、监督、审核及接力，不把缺失当零 |
| 已经安全停下了吗 | 不再调度、原生进程仍运行、停止未确认、资源保护保留等分别说明；有残留或副作用时指明 |
| 现在需要用户决定什么 | 具体问题、可选处理、推荐及影响；可以接受本阶段、要求调整、先补验证、暂停或终止，不能用泛泛“是否继续”掩盖关键选择 |
| 证据与历史在哪里 | 本轮产物/审核/执行证据的有效入口；保存失败、材料已清理、链接不可访问或输出截断明确说明 |

非适用项可以省略，关键未知不可省略。展示的信息取自现有权威与实际产物；不为凑模板虚构结果，也不要求输出模型内部思维过程。默认使用用户要求的语言，诊断错误保留必要原文。

### 7.2 不同类型轮次的实际成果

| 轮次类型 | 主要交付 | 本轮不应宣称的完成 |
|---|---|---|
| 需求澄清 | 用户场景、功能边界、必要非功能约束、待确认项、预期效果与验收方向 | 产品已实现 |
| 资料研究 | 带来源、版本、时间和适用范围的结论，候选比较与未知项 | 选型已通过本机集成验证 |
| 方案/阶段计划 | 总体路线、阶段成果、依赖、当前阶段任务与分工、验证方法 | 计划存在就已获开发授权 |
| 开发 | 实际源码/配置差异、可用成果及相关自测、兼容与使用说明 | 代码生成或构建成功就完成全部需求 |
| 测试 | 对应版本和环境的结果、失败复现、覆盖与未验证范围 | 只打印测试命令就通过 |
| 独立审核 | 结论、定位与证据、风险/限制、建议以及是否写入证据链 | 没有 verdict、审核不可用或未运行等同 PASS |
| 集成/阶段验收 | 各交付的来源与实际消费、集成验证、需求覆盖、遗留项、用户决策材料 | 多个成员结束就已集成，阶段完成就项目完成 |
| 中断/拒绝/取消 | 停止原因、已有有效成果、未执行下游、部分写入与停止事实、可选后续 | 没有正常答案就什么都没发生，或换模型即可无损继续 |

验收项在需求阶段定义到足以判定结果；测试角色可补边界，但不能为让失败变通过而擅自修改需求或削弱原有验证。确需修正错误测试或验收时说明依据和影响，走相应用户确认。

## 8. 需要明确的边界场景

以下是系统性查漏清单，不是本轮发现的全部现存缺陷，也不承诺穷尽所有风险；与已有契约重复的部分用于明确产品表现，不另建基础设施。未标为用户已选的新增处理规则仍待审阅。

### 8.1 需求、计划与用户决策

| 触发情况 | 建议规则 |
|---|---|
| 用户只给一句大概需求 | 先探索和澄清，集中问会改变范围/方案的问题；不补齐臆想功能后直接开发 |
| 不同模型理解不一致 | LAYA 列出分歧、依据和选项；涉及用户意图的分歧交用户决定，不按模型多数票改需求 |
| 用户后续意见与旧计划冲突 | 明确变更点、受影响任务和已有成果；确认新范围，再使相应旧计划/验收失效 |
| “可以”“继续”等回复含糊 | 按当时展示的对象解释，不把认可设计扩大为整项目实施授权；确有歧义才澄清 |
| 用户长时间未回应 | 保持等待，不因超时、沉默或模型自评自动批准 |
| 用户要求简化流程或合并阶段 | 可提出适合范围的简化方案，由用户决定；模型不能自行跳过已约定确认点 |
| 性能、离线/联网、数据保存、兼容性等未说明 | 只澄清会影响选型、验收或实际使用的必要约束；不把所有企业级要求强加给个人工具 |
| 多个独立目标混在一个需求里 | 先区分目标、依赖和交付边界；是否合并阶段由 LAYA 提案并交用户确认 |
| 假设被实际调查否定 | 保留已有效成果，说明方案为何不成立与最小调整；不悄悄改需求以宣称成功 |

### 8.2 角色、上下文、模型与工具

| 触发情况 | 建议规则 |
|---|---|
| 用户模型池无法覆盖某职位 | 可以合并兼容职责或报告能力缺口；不虚构新模型、不擅自开付费资源 |
| 模型名字相同但版本/端点/工具不同 | 以实际 Agent × Model × 配置/工具组合及证据描述能力；未经确认的实际身份标未验证 |
| 模型列在目录但已退役、无权限或限流 | 目录不当可调用证据；显示具体拒绝/未知原因，按当前准入处理 |
| 一个模型兼任多个职责 | 区分输入、产物和角色责任；独立审核与开发保持独立会话和材料核对，不以换提示词冒充独立性 |
| 上游未交付、材料缺失或来源不明 | 下游不把它当已验收前提；列缺什么，先补证据或交用户决定 |
| 长上下文被截断、研究结论被摘要改写 | 保留原始引用与截断标记，关键约束和接口单独传递；按需读取，不广播所有对话 |
| 历史记忆与当前源码/要求冲突 | 历史只作参考，核对当前事实与适用版本；记忆不授权操作、不决定任务状态 |
| 工具权限改变、Skill/MCP 缺失或仅被请求 | requested、admitted、实际调用和结果区分；必要工具不可用时报告，不能谎称使用了工具 |
| 搜索没有找到来源，或只有相互转载 | 报告未找到/未核验，区分官方陈述、社区经验与推断；不编造出处或把搜索摘要当源码验证 |
| 多模型意见形成回音壁、重复调查 | 任务目标和交付区分，避免仅相互转述；是否值得多模型用实际结果与协调成本判断 |

### 8.3 执行、工作区与不可逆副作用

| 触发情况 | 建议规则 |
|---|---|
| 断流、超时、额度、认证、服务崩溃或长时间静默 | 区分已观察故障与未知，静默不直接判死亡；错误不自动归因于模型能力 |
| 失败前已写文件或执行外部动作 | 先检查现场和副作用，不能整任务盲重放；报告已做/未做/不确定部分 |
| 一个成员失败、其他成员成功 | 保留有效成果，说明被阻塞下游；不把全部任务都当失败，也不把部分成功当集成完成 |
| 请求暂停、取消、停止或换模型 | 区分停止后续调度、原生取消和可保存检查点；不承诺任意进程能原地冻结恢复 |
| 旧进程树停止尚未确认 | 复用现有 quarantine/lease/resource claim 保护，不提前释放，不启动第二个有效写者 |
| 编排器崩溃或系统重启 | 先核对存活进程、工作区、未完成操作与持久证据；不能仅恢复聊天记录就自动续写 |
| 用户或其他工具在运行中修改同一工作区 | 标明本轮起点与实际差异，发现冲突时停止相关写入并交用户决定；不覆盖或清理用户改动 |
| 非 Git、未提交更改、文件锁、大小写/路径/编码差异 | 说明真实隔离与回退能力；非 Git 不承诺可 reset，Windows 关键路径与命令需实际核验 |
| 不同任务争用端口、服务、缓存、数据库或外部账户 | 文件范围不同不代表资源独立；复用既有资源声明与准入，隔离不足就顺序执行或拒绝 |
| 推送、发布、删除、迁移或其他外部副作用 | 按用户已有授权与具体范围处理；模型建议和阶段开发授权不能自动覆盖不可逆动作；回滚能力不明时如实说明 |
| 连续重复同一失败、反复切模型或重规划 | 受现有次数/预算和关口限制；提交失败证据与可选处理，监督者纠偏仍交用户，不建立无限循环 |

### 8.4 成果、验证、报告与数据

| 触发情况 | 建议规则 |
|---|---|
| 声称完成但无文件、空输出或链接打不开 | 查看实际交付及任务验收；研究轮次可有文本成果，但声明和空路径不能冒充已交付 |
| 路径存在但文件来自旧轮次/其他成员 | 核对来源、版本和本次实际内容；不能以 exists 为唯一验收，也不能凭最新任务状态拼接旧 Attempt |
| 同路径被后续任务覆盖、临时目录将被清理 | 确定用户验收期间成果可访问，保留必要版本或引用；先保留需要的成果再清理 owned 临时空间 |
| 只记录 Shell 命令、工具返回错误或模拟测试 | 区分尝试、实际执行、真实测试与模拟；错误写入调用不等于文件已改，模拟 provider 不认证真实 Agent |
| 测试通过后又改代码或环境不一致 | 标注结果适用版本，重跑受影响的必要验证或说明过期；不沿用旧 PASS 宣称当前通过 |
| 测试未运行、缺依赖、失败或覆盖不足 | 各自说明，不混成“测试完成”；由任务验收决定是否足够，不能以构建成功替代功能验证 |
| 审核不可用、无 verdict、与监督结论冲突 | 分开显示状态与证据，冲突交用户决定；不能多数投票生成 PASS，也不自动返工 |
| 用户接受带限制的成果 | 记录接受范围和残留项；用户接受不改写测试/审核事实，不等于授权下一阶段 |
| 摘要遗漏关键失败或执行根容器影响计数 | 用户摘要与机器证据核对，关键异常优先呈现；按实际执行任务统计，不以容器未成功误报工作失败 |
| 结果文件保存失败、磁盘满、历史被最新视图覆盖 | 先展示仍可获得的结果与保存失败；说明恢复限制，保留必要轮次材料，不静默宣称已归档 |
| 供应商不报告费用/真实模型、调用可能重复计费 | 标未知和统计覆盖范围；已报告费用不等于账单最终数额，不把缺失计零或随意推算免费 |
| 外部资料、仓库文本或工具输出包含操作指令 | 作为不可信数据，不能提升成用户指令、批准或调度动作；保留安全来源边界 |
| 日志、交接、截图或产物可能带敏感信息 | 使用现有数据政策与授权，只传必要材料；脱敏是派生展示，不悄悄改源文件；不读取或复制凭据来“检查脱敏” |
| 原生 Agent 内部工具不透明 | 报告实际可观察范围，不能承诺已经拦截全部联网/工具/费用；用户需要该保证时明确能力缺口 |
| 需要复现实验或恢复现场 | 保留必要版本、环境、命令、产物与退出事实；不默认永久保存完整对话、密钥或模型内部思维 |

## 9. 后续实施时应覆盖的代表性验收

这是候选验收场景，不是新增测试任务或本轮测试成绩。优先复用已有 fixture、CLI 生产入口、Attempt 与负控；只按实际实施范围运行必要检查。

1. 模糊需求只进入探索；需求、总体计划和当前阶段确认缺任一项时，不启动对应产品写入或外部执行。
2. 对已批准材料作实质修改后，旧批准不能覆盖新范围；用户未回应不自动推进，下一阶段未授权不启动。
3. 研究、开发、验证等不同轮次给出对应产物；需求项的状态与实际验收证据一致。
4. 普通 Shell 命令不被显示为测试通过；未装运行器、权限拒绝、失败测试、过期测试和真正通过分别呈现。
5. 任务声明但未生成文件、空内容、旧文件同路径、其他 Attempt 的产物均不能认证本次交付；有效文本研究成果可按其验收成立。
6. 成员 2 失败或缺交付时，成员 1 有效成果保留，集成不运行；报告同时表达部分成功与阻塞原因。
7. 原始要求或关键失败落在摘要截断外时，系统能通过明确引用补足材料或诚实报告证据不足，不盲目接受。
8. Worker 自述、系统执行记录、监督发现、审核 verdict 与用户验收不相互替代；审核不可用/失败/缺证据不显示为通过。
9. 模型目录有记录但不可调用、fixed 不可用、必需 MCP/Skill 缺失时启动前拒绝，保留原因，不偷换模型或费用政策。
10. 断流发生在文件写入之后，不盲目重放；进程树停止未确认时保留保护，接力写者不能启动。
11. 用户修改工作区、端口/服务冲突、非 Git 环境和临时产物清理分别覆盖其真实支持边界，不删除用户数据。
12. 报告写入失败不篡改执行结果；最近结果投影、历史材料与恢复状态区分，重启后不凭聊天记录直接恢复写入。
13. 恶意网页/仓库/记忆文本不能成为新指令或授权；跨模型材料与报告遵守数据政策，未知可见性明确显示。
14. 一次成功与一次受阻的用户交付材料均包含产物入口、验证范围、未知项和具体决策；未知费用不为零，整轮统计不遗漏审核/接力等成本。
15. 将少量相近任务在单模型与多模型方式下按同一验收比较交付质量、耗时、消耗和返工；不预先承诺动态分工一定更省或更准。

## 10. 本轮新增研究依据与适用限制

本轮 GitHub MCP 检索及文件读取成功；部分 arXiv HTML 全文请求连接失败，论文核对以可访问摘要、官方架构文档与相关实现为限，未完整复核或复现论文实验。下表的“本项目启发”是设计推断，不是论文对本项目效果的证明。

| 一手来源 | 直接支持的事实 | 本项目启发与限制 |
|---|---|---|

## 13. 对已识别缺口的最小解决建议

以下描述“用什么已有能力、补什么行为、怎样验证”，供后续任务选取；不是要求一次实现全部，也不提前确定新的文件名、通用协议或数据库。

### 13.1 需求、计划与执行授权

**建议办法：** 用户审阅的材料优先使用普通 Markdown/设计图；保留原始需求、用户修订和明确批准所指向的版本/范围。LAYA 将已确认材料转成现有有界计划候选，再走 plan-file/Planner/Assignment/Spawn Gate。计划文件能解析、只剩一个合法候选或模型自己说“批准”，均不替代用户授权。

在进入产品写执行前核对当前阶段授权和材料适用性；不要仅依赖提示词要求 Worker 自律。准备材料/只读研究与产品实现的允许行为分别记录。已获授权阶段内正常任务推进不重复向用户确认每条命令。

**最小验证：** 没有需求或阶段批准时实现 Worker 不启动；批准其他阶段不能通用；用户修改关键需求后旧批准不覆盖新内容；仅调整排版不会迫使所有历史任务重跑。

### 13.2 长材料与跨角色交接

**建议办法：** 保留有界摘要作为导航；长研究、接口规范、方案与验收放到明确的交付物中，用既有 Task.artifacts 传递。Brief 附当前已确认约束、必要接口要点、交付物位置/适用版本和未解决问题；下游使用自身读取工具核对所需部分。短文本成果可以直接交付，不强迫每个小任务生成文件。

路径必须指向下游实际能访问的内容。相对路径绑定其所属工作区，不能把上游 worktree 路径误当下游已有文件；材料已被替换、清理或来源不明就报告缺失。对批准后可能被替换的关键材料再使用内容指纹等最小校验，哈希不是所有产物的必填门槛，也不能充当权限授权。

**最小验证：** 核心接口定义位于长报告开头、摘要之外，下游仍能读取正确材料；引用不存在、文件已变或工作区不相通时不继续凭摘要猜实现；同名旧文件不能冒充本次成果。

### 13.3 用户交付、成果与真实测试

**建议办法：** 在现有 RoundResult 上提供简短交付视图：授权范围、需求验收对照、实际成果入口、有效验证、遗留项与用户决策。仍由 TaskStore/AttemptStore/同次 RunResult 提供事实，模型负责有出处的归纳，不成为第二个结果权威。

Task 声明的产物保留在任务层；本次观察到的交付及验证应有实际来源，不能为显示方便归入任意 Attempt。变更文件取工具事实和可用的工作区差异，相互补充；没有 toolCalls 不等于没有改动。

测试先区分普通命令和项目验证命令；结合 [ToolCall](../src/core/types.ts) 已有可选 exitCode、输出和错误说明适配器实际观察到的结果。缺逐命令退出码就标未核实，不拿整进程 exit=0 代替。通过结果关联所测代码/环境；用户后续改了相关内容，标为不再适用，而不是删掉历史记录。不要只用命令名正则作唯一真伪依据，项目自定义验证脚本也可有证据。

**最小验证：** pwd 不进入“测试通过”；npm test 失败、未安装运行器、工具拒绝和退出码未知分别呈现；审核不可用不变 PASS；声明路径未生成与实际文件有效分别呈现；摘要不会漏掉关键阻塞。

### 13.4 跨轮确认、历史材料与恢复

**建议办法：** 分两步处理。第一步只保留按轮次区分的结果、阶段交付索引及用户确认引用，复用既有结果发布和 NextRoundInput；下一轮由用户显式发起，读取正确版本材料并重新走准入。最近结果文件继续作为最新视图，不能当全部历史。

确认记录只描述用户批准的材料/范围和相关轮次，不复制一套可派工的任务状态机。知识型 memory 继续存参考事实；不由记忆摘要决定任务完成、批准或恢复现场。先用现有存储约定与少量本地文件，不为此引入数据库或工作流框架。

第二步才研究崩溃恢复：必须核对存活进程/资源保护、真实工作区、部分副作用和必要持久证据。只有历史聊天或单个 round-result.json 时允许查看结果/准备新计划，不声称可以恢复原生会话或无损续写。

**最小验证：** 两轮结果不会相互冒充；上一轮未确认材料不能当本轮批准；文件损坏/保存失败有明确说明；重启后不凭旧 running 标签启动第二个写者。

### 13.5 监督者的实际介入方式

**建议最小版本：** 先在需求/方案交接、开发任务执行结束待验收、集成前和阶段交付前进行只读检查。监督者提供“要求、证据、影响和建议”，发现需纠偏的问题就阻止后续相关派工并交用户，不自己改代码或发新任务。通过也不替代既有 Verification 和 Codex 审核。

监督模型无需逐条看完整工具流；先用当前需求、变更和必要证据，避免不断重复审核。普通检查点模式只能在这些边界发现问题，不能承诺任务运行中即时制止所有错误；是否另外要求实时监督仍待用户确认。

当前 Scheduler.stop 仅停止后续调度，不取消正在执行的任务；需要取消时沿 cancelTask/Runtime，等待物理停止事实，保护未释放前不接力。现有 Human Gate 仍按真实状态派生：有在途执行时不能强行标“轮次完成”；可以先展示待用户决策和当前执行状态，后续交互接线另行实现。

**最小验证：** 监督异常后下一依赖任务不启动，纠偏由用户决定；正在执行者的真实运行/取消状态仍可见；监督结果不能直接篡改 Task 状态或伪造轮次完成。

### 13.6 Git 项目的协作与集成

**当前处理：** 保持现有 Git collaborate 拒绝和 PARALLEL_WRITE=CLOSED，改进后续产品说明和可选路径，不把“去非 Git 目录运行”当作成熟 Git 项目解决方案，也不自动初始化仓库、清理脏工作区或去掉隔离检查。

**后续优先评估的方案：** 对一个顺序协作组使用独立的组工作副本，让成员与集成任务依次在其中读取同一组实际文件，各自仍有独立 task/session 与执行身份；资源/工作区归属和清理通过既有 Workspace/Claim/Lease 统一管理。成果作为组级差异和验证交付给用户，再走既有受控人工集成路径。它需要明确调整工作区契约，不能仅改 cwd 或把多个独立 worktree 宣称为共享目录。

如果需要保持成员独立 worktree，则另一方案是有界传递已核验的成员差异到集成者工作区，预检冲突与路径，保留来源后再验证。Git apply --check 只是适用性预检，不保证合并后的业务正确；不为首片引入通用自动合并引擎。两种方式应在该功能正式设计时比较并确认，不在本草案同时实现。

源项目未提交改动必须单独识别；新 worktree 不自动包含用户工作树改动。需要把未提交内容作为输入时由用户明确范围并安全保留，不以 clean-only 规则迫使用户提交、stash 或丢弃现有工作。

**最小验证：** 成员真实写出的文件能被集成者读取，来源和 task/session 身份正确；用户原工作树不被覆盖；脏文件、集成冲突、停止未确认和文件不可达均安全拒绝；最大有效写者仍为 1。

### 13.7 原生工具不可见与实际文件差异

**建议办法：** 有 Git 时，记录获授权执行前后的工作区状态与差异，包含必要的新增/删除文件信息；与当前 toolCalls 对照。差异归属以前置基准和排他写保护为前提，不能把用户同时编辑的文件全部归给 Agent。

无 Git 时仅在已确认范围或声明产物上观察必要变化；按需求保留可恢复输入，不全盘扫描/备份用户目录，不读取凭据以求“完整”。原生 Agent 有越界写能力而系统无法强制限制时，报告真实限制；快照不能替代沙箱，也不能保证发现所有内部动作。

**最小验证：** 纯文本适配器实际改了授权文件时，报告能显示已观察差异；没有观察能力时显示未知，不输出“没有修改”；检测到用户并发改动时归属不确定而非冒认。

### 13.8 不可信材料、脱敏与权限

**建议办法：** 在交接和审核中区分用户明确指令/批准与模型自述、网页、仓库、历史记忆和工具输出。外部内容以数据字段/引用传递，对会影响消息格式的内容作结构化编码和边界处理，不能解析成派工或批准。

跨模型发送材料和用户报告使用派生副本，按实际数据政策最小化，并在这些出口处理已知敏感模式；不要就地改原始日志或项目文件。核查默认日志/报告保存位置和访问范围，必要时不发送无法安全处理的内容，明确说明材料被省略及证据不足。模式脱敏会漏报或误报，不能保证覆盖所有秘密；本轮不读取真实凭据来测试。

原生 Agent 内部直接联网或传文件不一定经过编排器出口。按适配器的真实权限/沙箱能力声明保证；没有该能力就不宣传全链强隔离。Job Object、Git worktree、提示词标签和敏感模式过滤分别解决不同问题，不能互相替代。

**最小验证：** 合成恶意材料无法提升为用户批准或调度动作；合成令牌不出现在派生跨模型材料/用户报告中，原始项目内容不被改写；不可观察的原生调用明确标出边界。

### 13.9 故障分类、重复执行与安全接力

**建议办法：** 继续复用既有 continuation、身份、Attempt 链与停止协议。先判断 worker 不可用、实际任务错误、工具故障或未知，再决定有界处理；不要把所有非零退出都换模型重做。fixed 不偷换，费用授权不扩张。

恢复前核对哪些操作已发生、可重复、不可重复或未知。只读步骤或有证据的幂等步骤可以在已授权范围内重新执行；写文件、推送、发布、迁移等不能因没有收到成功响应就断定未发生。无法确定时展示现场与选择给用户；监督触发的纠偏仍全部交用户。

不能承诺任意原生工具“恰好执行一次”；本地步骤完成记录也不能单独证明远程副作用没重复。远端支持操作标识/状态查询时复用，否则保留不确定性。停止未确认时不换写者。

**最小验证：** 写完文件后响应断开不会盲重放；普通测试失败不被当额度耗尽接力；重试上限/预算、fixed 与未停止保护仍生效；未知外部副作用保持待确认。

### 13.10 部分写入、回退与清理

**建议办法：** 执行前明确工作区来源和本次允许改动，保留实际需要的恢复材料。Git 隔离副本交付差异，非 Git 对已授权范围按需保留可恢复版本；不默认创建全量 .bak，不把失败等同于自动回滚授权。

用户决定回退时先对照当前工作区，保护之后新增的用户改动。代码回退不能撤销已发布服务、远程数据或其他外部副作用；删除临时副本前先确认其中是否仍有唯一成果。停止不明、归属不明的目录保留并报告，不顺手清理。

**最小验证：** 中断后已有有效成果保留；回退不删除用户后续修改；非 Git 无恢复证据时如实说明；临时工作区删除前成果已交付且原执行停止得到确认。

### 13.11 消耗、预算与模型信息

**建议办法：** 从同次 RunResult/Attempt 及实际决策调用汇总供应商报告的用量和耗时；有缺项时同时显示已知部分与覆盖范围，保留计量来源。编排 budget units、token、货币、订阅剩余额度分别显示；不能跨单位相加，也不把估算当账单实扣。

不预先强制新增某个 consumption 字段或把 unknown 填成字符串占用数字字段；具体类型沿既有契约最小扩展。报告实际模型无法核实时保留“请求模型/已观察身份”的区别。能力资料保留版本与时间，更新资料不自动扩大用户模型池或费用授权。

**最小验证：** 执行费用已知但审核费用未知时不显示“全流程费用已知”；返回 0 与未报告分别呈现；重试/接力不重复记同一次调用，缺真实实际模型时不伪造身份。

### 13.12 收益与验证投入

**建议办法：** 先复用已有 hermetic 生产调用链及负例检查接线，再在用户授权范围做少量真实 Agent 任务，检查产物、关键交接和失败处理。能力选择以官方/可信社区材料起步，本地证据补充；不为了分配模型先建立庞大能力平台。

比较多模型与单模型时保持目标、初始材料、验收要求和大致资源条件可比，观察完成质量、总消耗、延迟与返工。结果不够时保留未知，多模型收益不足可合并职责，不能为证明架构先进而增加模型数量。

**最小验证：** 一个正常交付与一个受阻交付都能给用户有效决策材料；fixture 成功不冒充真实兼容；存在反例时不宣称普遍节省或正确率提升。

## 14. 补充的一致性问题与研究来源

### 14.1 容易在实施中遗漏的细节

| 情况 | 最小处理建议 |
|---|---|
| 用户重复批准、重复点击继续或同一恢复请求重复提交 | 批准绑定具体阶段/材料版本；启动前核对是否已有有效执行，复用既有 lease/claim 防双写；重复请求不自动生成第二次执行 |
| 用户查看报告后代码或产物被其他工具改动 | 报告保留适用版本，当前差异与旧验收分开；接受旧报告不自动验证当前文件 |
| 报告来源混用旧 task 状态、最新 RunResult 和其他 Attempt | 复用同次证据关联；无法配对则 missing/unknown，不以“最新”补齐 |
| 需求改变但只有部分模块受影响 | 复核受影响交付/验证与批准，保留无关有效成果；不把历史 succeeded 全部改写或全量重做 |
| 需要关键 MCP/Skill，但当前 Brief 把技能表述为“没有也继续” | 区分推荐工具与必要能力；必要项在既有准入/真实能力层检查，不仅在提示词换成“必须”；该完整链路仍属后续 B3 |
| 监督发现疑点，但不能证明违反要求 | 报告疑点、影响及缺少的证据；不要伪造成已证实违规。是否需暂停按已约定规则与实际风险交用户处理 |
| 编排器与原生 Agent 对权限、自动批准或停止有不同语义 | 报告两层配置与可保证范围，不把外层计划批准当成原生全部内部动作可控；启动时仍服从既有能力与权限检查 |
| 保存材料的路径恰好在将被清理的工作区内，或符号链接/junction 指向范围外 | 检查实际归属与可访问性，避免越界读取/清理；保留必要交付再清理，不认为字符串路径前缀即可证明归属 |
| 长时间等待用户或外部条件后继续 | 重新核对受影响的模型可用性、材料版本、执行保护和费用授权，不沿用过期事实；不要求重做所有无关已确认内容 |

这些检查是后续相关变更的验收候选，不新增本轮测试、不自动打断当前前置任务，也不把“有一种理论可能”列为已存在 P0。

### 14.2 补充调研依据

- [LangGraph 持久化官方说明](https://docs.langchain.com/oss/javascript/langgraph/persistence)：区分线程检查点与跨线程记忆；支持将知识记忆和执行/确认材料分开理解，不代表本项目应引入 LangGraph。
- [LangGraph interrupts 官方说明](https://docs.langchain.com/oss/javascript/langgraph/interrupts)：恢复时节点会从头执行，interrupt 前的代码会再次执行。这说明“支持恢复”并不自动消除副作用重复；本项目应先明确步骤与实际执行事实，而非直接套暂停 API。
- [Microsoft Job Objects 官方说明](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects)：管理进程组、资源限制和终止，安全限制需针对进程另设；不能据此推出已隔离文件/网络权限。
- [Git worktree 官方说明](https://git-scm.com/docs/git-worktree)：额外工作树与仓库的关系可用于后续组级工作副本评估；共享部分 Git 元数据的限制继续遵守现有架构契约。
- [Git apply 官方说明](https://git-scm.com/docs/git-apply)：--check 检查补丁适用性而不实际应用；它只能是受控集成的预检之一，不提供业务验收或全面冲突解决。

以上只研究机制和边界，未复制源码、安装框架、创建 worktree、运行补丁应用或改动权限配置。新增建议继续等待用户后续任务，不把参考报告的判断或本草案的方案当成当前实现事实。
